# Аудит фильтров на сайте demo.garant.ru (режим `browser`)

Дата аудита: 09.09.2026
Метод: разовый исследовательский скрипт на базе уже рабочего Playwright-логина (`GarantPrimeParser`), см. ТЗ `tz/tz-garant-news-filtering.md`, раздел 3.1.

## Результат: аудит не завершён — вход не удался технически, повтор не выполнялся

Скрипт повторил ровно тот же сценарий входа, что уже подтверждён и работает в `core/news/parser_browser.py` (SSO `account.garant.ru`, посимвольный ввод через `page.keyboard.press`, `playwright-stealth`). Переход на страницу пароля прошёл штатно (сайт узнал логин, показал «Введите пароль от аккаунта 545»), но сама попытка входа была отклонена сайтом («Неверные данные»).

**Наиболее вероятная причина — не проблема с самими учётными данными или блокировкой сайта, а техническая флуктуация посимвольного ввода**: скриншот (`debug_news_tab_not_found.png`, сохранён локально в scratchpad-директории сессии, не в репозитории) показывает в поле пароля **3 точки**, хотя `GARANT_PASSWORD` — 4 символа. Похоже, один символ был потерян при быстром `page.keyboard.press` без пауз между нажатиями — тот же механизм ввода, что и в `_type_into` (`parser_browser.py`), но там, судя по всему, это случается достаточно редко, чтобы не быть замеченным на подтверждённом 06.09.2026 прогоне.

**Решение — не повторять попытку входа немедленно.** Сайт явно не любит частые повторные входы одним аккаунтом (см. докстроку `parser_browser.py`, `MIN_SECONDS_BETWEEN_LOGINS`), а несколько попыток подряд с ошибкой пароля увеличивают риск более серьёзной блокировки аккаунта, чем обычный `alreadyused`. Поэтому глубокий UI-аудит (пункты 1-4 ниже) в этой итерации **не выполнен** — это осознанно отложено, а не пропущено по невнимательности.

## Что подтверждено этим прогоном (несмотря на неудачу)

- Сценарий входа (клик "Войти" → SSO `account.garant.ru` → шаг логина → шаг пароля) воспроизводится идентично тому, что описан в `parser_browser.py` — никаких структурных изменений вёрстки страницы входа не обнаружено.
- Страница входа теперь дополнительно показывает номер аккаунта («аккаунта 545») после ввода логина — мелкая деталь, не влияющая на код `_login_to_garant`.

## Не проверено (требует отдельного повторного прогона)

1. Есть ли на вкладках «Общая лента ПРАЙМ»/«Новости ПРАЙМ» видимый UI-фильтр по категориям/темам, и совпадает ли он с деревом `GET /v2/prime`.
2. Работает ли гипотеза маршрута `/#/fresh/DD.MM.YYYY;DD.MM.YYYY` для фильтрации периода через URL.
3. Есть ли текстовый поиск на этих вкладках.
4. Прочие фильтры (регион/орган/тип) с CSS-селекторами.

## Рекомендация для реализации этой итерации

Раз аудит сайтовых фильтров не завершён, а официальный API (`GarantApiParser`) уже подтверждён живым вызовом (`GET /v2/prime` вернул реальное дерево категорий, см. README) — **режим `browser` в этой итерации остаётся без фильтрации категорий/территории/вида информации** (как и было, без регрессий), режим `api` — основной для точной фильтрации. Это соответствует явно допустимому по ТЗ исходу («если аудит покажет, что фильтрация на сайте либо отсутствует, либо ненадёжна... это тоже валидный результат»).

## Как повторить аудит позже

Подождать заметный интервал (не сразу, из соображений раздела выше), затем можно переиспользовать `core/news/parser_browser.py::GarantPrimeParser._login_to_garant`/`_type_into` напрямую (они уже проверены end-to-end) вместо копии в разовом скрипте — это исключит саму гипотезу о флуктуации ввода как причине неудачи. Если ошибка повторится с тем же результатом (только 3 из 4 символов пароля) — стоит добавить небольшую паузу между `page.keyboard.press` в `_type_into` (например 30-50мс) как более надёжное решение и для продакшн-кода, а не только для аудита.
